# Message Board — HW-02

A realtime message board for CSC 4360 (Mobile App Development), Homework-02. It
opens with a styled splash screen, registers and signs in users with Firebase
Authentication, writes a private Firestore user record on every registration,
and backs a public message board with full create / read / update / delete —
all streamed live and guarded by security rules.

- **Focus:** Firebase Auth · Cloud Firestore CRUD · Security Rules
- **Platform target:** Android (release APK included as a separate deliverable)

## Features

- **Splash screen** that holds while Firebase initializes, with a retry path if
  initialization fails.
- **Firebase Authentication** (email + password): registration, sign-in, and
  sign-out, all centralized in `AuthService`.
- **Auth-state routing** driven by `authStateChanges()` — signed-in users land
  on the board, signed-out users land on login.
- **Firestore user record** written on registration with all five required
  fields: `uid`, `firstName`, `lastName`, `role`, `registrationDateTime`.
- **Message CRUD** on a public `messages` collection, centralized in
  `BoardService`: create, live-stream read, update, delete.
- **Live stream** via `snapshots()` — a second device's post appears without a
  refresh.
- **Ownership rules** as their own layer — a signed-out read and a cross-user
  update/delete are denied by Firestore, not by hidden UI buttons.
- **Idempotent create** (Spice #4): a deterministic document id makes a
  repeated post target one document, so a double-submit leaves one message.
- **Automated rules tests** (Spice #2) using `@firebase/rules-unit-testing`.
- **Emulator workflow** (Spice #1) documented below, so the app and tests can
  run against the local Firebase Emulator Suite without touching production.

## Data model and storage design

Cloud Firestore holds one database with two deliberate sides, so public board
content is never mixed with private per-user data.

| Document | Fields | Writer | Access |
| --- | --- | --- | --- |
| `messages/{msgId}` | `text`, `authorUid`, `authorName`, `createdAt`, `editedAt` | Signed-in user (create/update of own only) | Public read for any signed-in user |
| `users/{uid}` | `uid`, `firstName`, `lastName`, `role`, `registrationDateTime` | Client once, at registration | Private to that `uid` |
| `users/{uid}/prefs/notifications` | (reserved) opt-in flag, token, `updatedAt` | Callable/rules-guarded | Private to that `uid` |

Design decisions:

- **`authorUid` is written at create time and never trusted on update/delete.**
  The rules compare it against `request.auth.uid`, so a forged owner is
  rejected at the door.
- **`createdAt` and `editedAt` use `FieldValue.serverTimestamp()`**, so ordering
  follows one trusted server clock instead of whatever the device reports.
- **The `role` field is descriptive only.** It is stored because the assignment
  requires it, but no access decision is made from a client-written role.

## Setup

### 1. Prerequisites

- Flutter (stable), the Android SDK, and a connected device/emulator.
- The Firebase CLI and the FlutterFire CLI.

```bash
flutter doctor                 # resolve Android/device issues first
dart pub global activate flutterfire_cli
```

### 2. Firebase project

1. Create a Firebase project and enable **Email/Password** under
   Authentication → Sign-in method.
2. Create a **Cloud Firestore** database.
3. Run `flutterfire configure` (select Android) to generate
   `lib/firebase_options.dart`:

```bash
flutterfire configure --project YOUR_PROJECT_ID --platforms=android,web
```

> `lib/firebase_options.dart` is public client config, not a secret. Never
> commit service-account credentials, tokens, or passwords.

### 3. Dependencies and rules

```bash
flutter pub get
firebase deploy --only firestore:rules --project YOUR_PROJECT_ID
```

### 4. Run

```bash
flutter run
```

## How to test

### Manual smoke test (after every build pass)

1. Register → sign in → the board loads (empty state or existing messages).
2. Post a message → it appears instantly via the stream.
3. Post again → verify exactly **one** new document in Firestore, not two.
4. Edit and delete your own message → the board re-renders from the stream.
5. Run the rules denials below, then fix one thing at a time.

### Rules denial drills

- **Signed-out read** of `messages` → denied by Firestore.
- **Cross-uid update/delete** of another author's message → denied with
  `permission-denied`.
- **Forged `authorUid` create** → denied by the create rule.

Each denial comes from the database, not from hidden buttons.

### Full app ladder

1. Register → sign in → post → hot-restart (`R`) → still signed in, board intact.
2. Stop and relaunch the app → session and Firestore data both restored.
3. Post from a second device/window → the first updates without a refresh.

## Emulator workflow (Spice #1)

Run the app against the local Firebase Emulator Suite instead of production:

```bash
firebase emulators:start --only auth,firestore
```

Then launch the app with the emulator flag (host is `10.0.2.2` from an Android
emulator; use `localhost` for web/desktop):

```bash
flutter run --dart-define=USE_EMULATOR=true --dart-define=EMULATOR_HOST=10.0.2.2
```

The release APK never sets `USE_EMULATOR`, so it always talks to production.
The Emulator UI (http://localhost:4000) shows seeded users/messages, and real
project data is untouched.

## Automated rules tests (Spice #2)

The `rules_test/` directory runs the security rules through the Firestore
emulator and proves the denials automatically:

```bash
cd rules_test
npm install
cd ..
firebase emulators:exec --only firestore "cd rules_test && npm test"
```

Covered cases: signed-out read denied, signed-in read allowed, correct-author
create/update/delete allowed, forged `authorUid` create denied, cross-uid
update and delete denied, and private user records limited to their owner.

## Idempotent create (Spice #4)

`BoardService.createMessage` accepts an explicit document id. The compose
screen mints one id per post and reuses it on retry, so calling post twice with
the same id leaves exactly one document rather than two. Combined with
disabling the submit button while a write is in flight, a double-tap produces a
single record.
